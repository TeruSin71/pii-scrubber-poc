PII Scrubber — AI Core Deployment Runbook

POC package for BTP Free Tier. Deploys to SAP AI Core (BYOM) — no Cloud Foundry, no Generative AI Hub.

Verified — and this runbook has now been executed end to end. The service is deployed and RUNNING on SAP AI Core (deployment d5e6ea76217ed207, image ghcr.io/terusin71/pii-scrubber:1.1.0, linux/amd64). Two different numbers, and only one of them is quotable:

96.4%  holdout recall — 107 of 111 planted values, on 40 samples never used for tuning. This is the figure to quote.

The self-test still returns recall_pct 100.0 (45/45, 0 misses, 6 over-detections), but that is a regression baseline, not a result — the recognizers were tuned against those same 13 samples, so 100% is close to guaranteed. Its job is to prove that packaging and deploying changed nothing.

Presidio + nine custom SAP recognizers, engine=presidio. Four real defects were found and fixed before deployment (see “What testing caught”), and a fifth — no street-address recognizer at all — was closed afterwards, taking ADDRESS from 0/3 to 3/3 on the holdout.

Deployment steps

1. Build & push the image YOU

Needs Docker and a registry account. This project uses ghcr.io; the PAT needs Packages: write to push and only read:packages for AI Core to pull.

The --platform flag is mandatory on Apple Silicon. SAP AI Core runs x86_64. A native build on an ARM Mac produces an arm64 image that pushes, pulls and verifies by digest perfectly — and then fails at pod start with exec format error. A digest check cannot catch this; check the platform explicitly.

cd pii-scrubber-poc
docker buildx build --platform linux/amd64 \
  -t ghcr.io/YOUR_USER/pii-scrubber:1.1.0 --push .

# verify the platform, not just the digest
docker buildx imagetools inspect ghcr.io/YOUR_USER/pii-scrubber:1.1.0
#   -> must list  Platform: linux/amd64

Emulated amd64 builds are cheap here (~3 min): pip installs prebuilt manylinux wheels, so QEMU emulates almost nothing. If a build dies with lease does not exist: not found, that is a corrupted BuildKit lease, not disk or network — docker pull the base image and rebuild unchanged.

Build takes a while — torch + GLiNER weights are baked in. To build a slim Presidio-only image, comment out gliner and torch in requirements.txt and the GLiNER prefetch block in the Dockerfile.

Test it locally first — this is the cheapest possible failure:

docker run -p 8080:8080 YOUR_USER/pii-scrubber:1.0.0
curl localhost:8080/health
curl localhost:8080/v1/selftest        # expect recall_pct: 100.0

2. Docker Registry Secret in AI Core YOU

AI Launchpad → SAP AI Core Administration → Docker Registry Secrets → Add. Name it docker-registry-secret (matches the template).

{".dockerconfigjson":"{\"auths\":{\"https://ghcr.io\":{\"username\":\"TeruSin71\",\"password\":\"PAT\"}}}"}

The host must match the registry you actually pushed to. https://index.docker.io is Docker Hub; using it against a private ghcr.io package does not error — the pull simply runs unauthenticated and the deployment fails with UNAUTHORIZED: authentication required during image resolution. The PAT here needs only read:packages; do not reuse a write:packages token, since this credential lives in BTP. AI Core has no secret-edit — to change it, delete and recreate under the same name.

3. Put the template in your Git repo YOU

Edit workflows/serving_template.yaml — replace the image: line, and nothing else. Commit and push to the onboarded repo. AI Core syncs roughly every 3 minutes.

Use the mutable tag, not a digest. A digest freezes the template to one build, so a corrected image needs a second template edit. The tag lets a rebuild flow through unchanged.

Three things here fail silently. All three cost a day.

  1. Path in Repository must be a real subdirectory. AI Core does not scan the repo root — an application configured with . syncs nothing and reports no error. Ours is workflows, which is why the template lives there rather than at the root.
  2. The sync status panel is cosmetic on free tier. A working application shows Sync Status: Unknown, Revision: Unknown, 0 synced resources — identical to a broken one. Do not diagnose from it. The only trustworthy evidence is the scenario and its executable appearing in §4.
  3. Repo onboarding status COMPLETED means “configuration stored”, not “repository reachable”. It never validates the credential. The git-sync token needs repo scope — a different scope from the registry secret in §2, and GitHub's 403 does not distinguish the two.

When something is wrong, go to the API rather than the cockpit — GET $AI_API/v2/admin/applications/{name}/status names the actual rejection reason the free-tier UI hides.

Template shape matters too. The scenario will not appear if the labels do not match what AI Core accepts: only scenarios.ai.sap.com/id and ai.sap.com/version. An executables.ai.sap.com/id label, or a version of "1.0.0" where the accepted templates use "1.0", is enough to prevent the sync producing anything.

4. Confirm the scenario appears YOU

ML Operations → Scenarios — pii-scrubber should show up alongside late-delivery and my-first-scenario.

5. Configuration → Deployment YOU

Configurations → Create: pick scenario pii-scrubber, version 1.0, executable pii-scrubber, set parameter engine = presidio. Then Create Deployment from that configuration. Wait for status RUNNING. First pull is ~2.5 GB.

The executable is pii-scrubber, not pii-scrubber-serve: with no executables.ai.sap.com/id label (see §3), it is identified by the template's metadata.name. The …/name annotation still reads pii-scrubber-serve and is cosmetic.

Free tier allows exactly one pod. Delete the old deployment before creating a new one — do not stop-then-create.

A stop-then-create race does not queue. The new revision is rejected at admission with exceeded quota: free-tier-resource-quota, pods=1 and is then marked failed permanently — Kubernetes never re-drives an admission-rejected revision, so it stays dead even after quota frees. Three deployments were burned this way before a clean-slate create succeeded. Delete everything else first, confirm nothing else exists in the tenant, then create one.

6. Call it YOU

# Token
curl -X POST "$AICORE_AUTH_URL/oauth/token?grant_type=client_credentials" \

# Self-test — the bake-off, running on BTP

7. GLiNER — blocked, do not attempt on this image YOU

This section previously said “create a second configuration with engine = both … No rebuild needed.” That was wrong. Setting engine = both against image 1.1.0 crash-loops the deployment.

TypeError: GLiNER._from_pretrained() missing 2 required
keyword-only arguments: 'proxies' and 'resume_download'

gliner==0.2.16 is incompatible with the huggingface_hub version pip currently resolves. The failing call is GLiNER.from_pretrained — exactly what get_gliner() invokes at runtime — so the failure happens on the first request, not at startup. The weights are not baked in either: the Dockerfile's GLiNER prefetch fails for the same reason and is tolerated by design, leaving a Presidio-only image.

It is therefore a dependency fix plus a rebuild, not a configuration change. Pin huggingface_hub in requirements.txt to a version whose hub_mixin.from_pretrained matches gliner's _from_pretrained signature, rebuild, and re-verify. Changing a pin is plan-authorized work requiring approval. The bake-off is a separate session.

What testing caught (before it reached BTP)

Three defects the self-test exposed. Each is now fixed and commented in the code — worth knowing because each would have been painful to diagnose inside a deployment:

  1. Outbound network call from inside the boundary. Presidio's UrlRecognizer fetches the public-suffix list from publicsuffix.org at runtime. Removed — a scrubber must not phone out.
  2. Case-insensitive regex. Presidio applies IGNORECASE by default, so the SAP user-ID pattern matched ordinary words ("stuck", "status", "sales"). 249 spans on 45 real values. Fixed with explicit case-sensitive flags.
  3. A leak caused by span ranking. spaCy labels 172.16.4.8 as DATE_TIME (0.85), which outranked IP_ADDRESS (0.60) — and DATE is not redacted, so the IP passed through in cleartext. Merge order now always prefers a redacting span over a non-redacting one, regardless of confidence.
  4. An entire entity type silently disabled by the library. presidio-analyzer==2.2.357 ships ORG and ORGANIZATION in its default NerModelConfiguration.labels_to_ignore, so spaCy's ORG entity was discarded at the NLP-engine layer before any recognizer ran — making an unsuffixed company name ("Pacific Traders") undetectable. get_analyzer() now rebuilds that ignore list minus ORG. The previously documented baseline had been measured on 2.2.364 installed unpinned; always install from requirements.txt when producing a number anyone will quote.
  5. No street-address recognizer existed at all — found by holdout evaluation, not by the self-test, because the tuned samples did not expose it. ADDRESS scored 0/3 while localities were caught incidentally, so output read the <ADDRESS> office at 22 Willis Street: tag present, identifying detail not. Closed 2026-08-15, ADDRESS now 3/3.

Honest limits of the 100%. It is 13 synthetic samples that I wrote — a sanity check, not proof. Two caveats: the sample set is small, and I tuned the recognizers against it, so some over-fitting is likely. Expect lower recall on real ticket text. Do not present 100% to management as the expected production figure.

This has now been measured, and the prediction held. A holdout of 40 samples written independently and never used for tuning scores 96.4% (107 of 111) — that is the quotable figure, and the gap between it and 100% is exactly the over-fitting described above. Four values still leak, in three classes: all-caps and bare surnames (ZHANG, Young), a full name spaCy simply missed (Mere Tuhoe), and a customer number keyed without leading zeros (1045567). Those are the tuning backlog and what the BPA human gate must catch. Expanding the set to 50–100 real-shaped samples remains the highest-value next step — every figure here still rests on 40.

Known over-detections (6 — re-verified 2026-08-15 on current code)

All safe-but-noisy — extra redaction, never a leak. Mostly spaCy's small model mislabelling technical phrases ("Invoice IDoc" → ORG, "PO" → ADDRESS). Ways to reduce them, in order of effort: the deterministic Z*/Y* custom-object rule (already implemented, CUSTOM_OBJECT_RULE=true), the allowlist per ALLOWLIST-EXTRACTION.md (now populated — 257,578 tokens from TSTC + DD02L), or switch SPACY_MODEL to en_core_web_lg.

Two corrections here. Enabling GLiNER is no longer on this list — see §7, it does not run. And the allowlist, though populated, did not reduce this count: none of the six is an SAP technical token, so no transaction-code or table-name list can reach them. PO is two characters and excluded by design as too collision-prone; "Invoice IDoc" is a two-word span the allowlist could not match at the time (whole-span exact matching; as of 2026-08-16 suppression is ALL-TOKENS, and this span is still not suppressed because "Invoice" is not an entry); Bill and Munich are spaCy mislabelling ordinary English. The remaining lever for this class is the SAP jargon glossary, still outstanding.

Free-tier watch-items

  • One pod. Exactly one. The quota is pods=1 across the tenant. Delete an existing deployment before creating another — a stop-then-create race marks the new revision failed permanently, not queued. See §5.
  • Memory. The starter resource plan is CPU-only and small. Presidio-only fits comfortably. If a deployment crash-loops, check the registry secret first (§2) — a private-package pull failure is the more common cause and surfaces as a generic image-pull error. Stay on engine=presidio; do not raise the resource plan, that has cost implications and is the account owner's call.
  • Not for real data. Free tier has no SLA and is resettable. Synthetic samples only.
  • Cloud Foundry is untouched. This uses none of your 3.44 GB / 4 GB CF quota.
