POC package for BTP Free Tier. Deploys to SAP AI Core (BYOM) — no Cloud Foundry, no Generative AI Hub.

Already verified before you deploy. The service was executed against the 13 labelled synthetic SAP samples in this session. Result:

100%  recall — 45 / 45 planted PII values redacted, 0 misses, 6 over-detections.

Presidio + custom SAP recognizers, engine=presidio, no GLiNER yet. Three real defects were found and fixed during that run (see “What testing caught”). You are deploying tested code, not first-draft code.

Deployment steps

1. Build & push the image YOU

Needs Docker and a registry account (Docker Hub is fine for a POC).

cd pii-scrubber-poc
docker build -t YOUR_USER/pii-scrubber:1.0.0 .
docker push YOUR_USER/pii-scrubber:1.0.0

Build takes a while — torch + GLiNER weights are baked in. To build a slim Presidio-only image, comment out gliner and torch in requirements.txt and the GLiNER prefetch block in the Dockerfile.

Test it locally first — this is the cheapest possible failure:

docker run -p 8080:8080 YOUR_USER/pii-scrubber:1.0.0
curl localhost:8080/health
curl localhost:8080/v1/selftest        # expect recall_pct: 100.0

2. Docker Registry Secret in AI Core YOU

AI Launchpad → SAP AI Core Administration → Docker Registry Secrets → Add. Name it docker-registry-secret (matches the template).

{".dockerconfigjson":"{\"auths\":{\"https://index.docker.io\":{\"username\":\"USER\",\"password\":\"TOKEN\"}}}"}

3. Put the template in your Git repo YOU

Edit serving_template.yaml — replace the image: line with your pushed image. Commit it to the repo already onboarded under Git Repositories (the same mechanism your sd-analytics scenario uses). AI Core syncs roughly every 3 minutes.

4. Confirm the scenario appears YOU

ML Operations → Scenarios — pii-scrubber should show up alongside late-delivery and my-first-scenario.

5. Configuration → Deployment YOU

Configurations → Create: pick scenario pii-scrubber, executable pii-scrubber-serve, set parameter engine = presidio. Then Create Deployment from that configuration. Wait for status RUNNING.

6. Call it YOU

# Token
curl -X POST "$AICORE_AUTH_URL/oauth/token?grant_type=client_credentials" \
  -u "$CLIENT_ID:$CLIENT_SECRET"

# Self-test — the bake-off, running on BTP
curl "$DEPLOYMENT_URL/v1/selftest" \
  -H "Authorization: Bearer $TOKEN" \
  -H "AI-Resource-Group: default"

# Scrub one text
curl -X POST "$DEPLOYMENT_URL/v1/scrub" \
  -H "Authorization: Bearer $TOKEN" \
  -H "AI-Resource-Group: default" \
  -H "Content-Type: application/json" \
  -d '{"text":"IDoc 51 for customer 0001045567, contact Aroha Ngata aroha.ngata@x.co.nz","mode":"batch"}'

7. Then turn GLiNER on YOU

Create a second configuration with engine = both and deploy it. Compare /v1/selftest between the two — that is your Presidio-vs-Presidio+GLiNER bake-off, measured on BTP. No rebuild needed.

What testing caught (before it reached BTP)

Three defects the self-test exposed. Each is now fixed and commented in the code — worth knowing because each would have been painful to diagnose inside a deployment:

  1. Outbound network call from inside the boundary. Presidio's UrlRecognizer fetches the public-suffix list from publicsuffix.org at runtime. Removed — a scrubber must not phone out.
  2. Case-insensitive regex. Presidio applies IGNORECASE by default, so the SAP user-ID pattern matched ordinary words ("stuck", "status", "sales"). 249 spans on 45 real values. Fixed with explicit case-sensitive flags.
  3. A leak caused by span ranking. spaCy labels 172.16.4.8 as DATE_TIME (0.85), which outranked IP_ADDRESS (0.60) — and DATE is not redacted, so the IP passed through in cleartext. Merge order now always prefers a redacting span over a non-redacting one, regardless of confidence.

Honest limits of the 100%. It is 13 synthetic samples that I wrote — a sanity check, not proof. Two caveats: the sample set is small, and I tuned the recognizers against it, so some over-fitting is likely. Expect lower recall on real ticket text. The number that will matter is the one you get after expanding to 50–100 samples drawn from the shapes your real tickets actually take. Do not present 100% to management as the expected production figure.

Known over-detections (6 — re-verified 2026-08-15 on current code)

All safe-but-noisy — extra redaction, never a leak. Mostly spaCy's small model mislabelling technical phrases ("Invoice IDoc" → ORG, "PO" → ADDRESS). Four ways to reduce them, in order of effort: the deterministic Z*/Y* custom-object rule (already implemented, CUSTOM_OBJECT_RULE=true), populate the allowlist per ALLOWLIST-EXTRACTION.md, switch SPACY_MODEL to en_core_web_lg, or enable GLiNER (engine=both).

Free-tier watch-items

  • Memory. The starter resource plan is CPU-only and small. Presidio-only fits comfortably; adding GLiNER may not. If the deployment crash-loops, that is why — stay on engine=presidio and raise the plan later.
  • Not for real data. Free tier has no SLA and is resettable. Synthetic samples only.
  • Cloud Foundry is untouched. This uses none of your 3.44 GB / 4 GB CF quota.
