KB Upload Path — CPI → NER Scrubber → BPA

Integration design for the build path. Extends the existing JIRA→CPI connection; frontend screens in SAP Build Apps; approval and restore in SAP Build Process Automation. Engine-agnostic: identical whichever scrubber engine ships.

Flow

JIRA (closed ticket, KB-source label)
  └─ existing CPI connection ── [NEW] iFlow branch
      1. call NER scrubber  POST /v1/scrub  (AI Core, OAuth2, serial)
      2. receive scrubbed text + token map
      3. persist { ticketId, raw, scrubbed, tokenMap } → HANA Cloud  (inside boundary)
      4. start BPA process with ticketId key
         └─ Build Apps review screen: original ⇄ scrubbed, restore-per-token from map
         └─ reviewer approves → entry is 100% clean
      5. [outbound — ONLY approved text] → variant classifier (Claude) → corpus

Boundary invariant, stated as a hard rule: raw text and token maps exist only in CPI, HANA and BPA — all inside the tenant. The single outbound hop is step 5, and it carries exclusively human-approved text. No iFlow branch may ever call an external service before BPA approval.

BPA process + review screen

  1. Process input: ticketId. Screen loads raw + scrubbed + token map from HANA by key.
  2. Reviewer sees original and scrubbed side by side; each placeholder is clickable → restore (from the map) or keep. Jargon false alarms ("plant ELEC", "Sls Org GGL") are one click each.
  3. Reviewer may also redact more (the residual the engine missed) — this is the gap-to-100% job the gate exists for.
  4. Approve → final text frozen; reject → back to queue with comment.
  5. Log every restore action (term, frequency). This log is the evidence feed the scrubber's allowlist rule requires — a term repeatedly restored by reviewers has earned per-entry protection consideration. Vocabulary grows from observed misfires, never from bulk loads.

Independent of the engine decision. Nothing here changes if management picks the current engine or the GLiNER union — only the timeout setting anticipates the slower engine. Phases 1–2 can start now against the live 1.2.3 scrubber.

Two things this design must never do: call any external service with pre-approval text (the boundary rule), and let anything but the scrubber + BPA reviewer touch raw data. If a future requirement seems to need either, it goes back to design review, not into a CPI branch.

Open decisions (small, non-blocking)

  • HANA Cloud vs CPI data store for staging — HANA recommended (the corpus needs a real store anyway; one persistence layer).
  • Expert-authoring entry point: same BPA process started from a Build Apps form (the architecture doc's option b) — decide when the review UI is built.
  • Retention: how long raw + token maps are kept after approval (compliance call — suggest deleting raw on approval, keeping only the clean corpus entry).
