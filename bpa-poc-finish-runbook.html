Finish the PII Scrub POC — step by step

Picks up exactly where we stopped. Everything below happens in SAP Build Process Automation, in the project PII Scrub and Review POC, process Scrub and Review Ticket. Roughly 30–45 minutes.

Already done — don't redo these. Destination NER_SCRUBBER (created, tested, flagged for Build). Action project PII Scrubber (released 1.0.0, published). Process created with trigger Upload Ticket → step Scrub PII from text → End, and the destination variable NER_SCRUBBER_DEST attached to the scrub step.

1Add the text box to the Upload Ticket form

The trigger form exists but has no fields yet, so there's nothing to scrub.

  1. Open the process Scrub and Review Ticket (Lobby → PII Scrub and Review POC → the process).
  2. Click the Upload Ticket trigger box, then in the right-hand panel choose Open Form (or the … menu on the box → Open Editor). The form editor opens in a new tab.
  3. From the left palette, drag a Text Area (multi-line) field onto the form canvas.
  4. Select it and set, in the right-hand properties:
    • Label: Ticket text
    • Name / Identifier: ticketText  (exact spelling matters — you'll pick it by this name in step 2)
    • Required: on
  5. Optional but handy: drag a single-line Text field above it — Label Ticket reference, Name ticketRef. Purely for labelling the run.
  6. Click Save, then close the form editor tab and go back to the process tab.

2Feed the form text into the scrubber

  1. Click the Scrub PII from text step.
  2. In the right panel open the Inputs tab (it has a red dot — that's what we're clearing).
  3. text — click the field, and from the process-content picker choose Upload Ticket → Ticket text.
  4. mode — type the literal word live.

    live is what makes the scrubber return numbered placeholders like <PERSON_1> plus the token map. batch would give you plain <PERSON> with no map.

  5. Click Save (top right). The red dot and the Design Console warning should clear.

3Add the review-and-correct step

This is the part the whole POC exists to show.

  1. On the canvas, click the + between Scrub PII from text and End.
  2. Choose Approval.
  3. Choose Blank Form and name it Review Scrubbed Ticket. The form editor opens.
  4. Build the form with three fields, in this order:
    Field typeLabelNameNotes
    Text (single line)Ticket referencerefDisplayOptional
    Text AreaOriginal ticket (reference only)originalTextSet read-only if the option exists
    Text AreaScrubbed text — correct it herecorrectedTextMust stay editable — this is the correction box
  5. Make the two text areas tall (5–10 rows) so real ticket text is readable.
  6. Save the form, close its tab, return to the process.
  7. Click the new Approval step → Inputs tab, and map:
    refDisplayUpload Ticket → Ticket reference
    originalTextUpload Ticket → Ticket text
    correctedTextScrub PII from text → scrubbed_text
  8. In the same panel set Recipients / Users to yourself (your email) so the task lands in your own inbox.
  9. Save.

The one mapping that matters: correctedText must come from the scrub step's scrubbed_text output, not from the form. If you map it to the original ticket text you'll be reviewing unscrubbed data and the demo proves nothing.

4Release and deploy

  1. Top right of the process editor: Release → version 1.0.0 → confirm.
  2. Then Deploy (the button changes after release).
  3. Deployment will ask you to give a value for the environment variable NER_SCRUBBER_DEST. Pick the destination NER_SCRUBBER from the list.

    This is the step that actually binds the process to the scrubber. It's a different mechanism from the Test tab that showed an empty list earlier, so don't be surprised if that one is still empty — it doesn't affect this.

  4. Confirm and wait for "deployed successfully".

If the destination isn't listed here either: stop and tell me. That would mean the destination genuinely isn't visible to BPA rather than just to the design-time tester, and it's a different fix.

5Run it

  1. Find the start form: project Overview → Triggers tab, which lists the deployed form and its link. (Alternatively, Monitoring → Manage → the deployed process.)
  2. Open the form link, paste the test ticket below into Ticket text, and submit.
  3. Open My Inbox (the inbox icon, top right of SAP Build). Within a few seconds the task Review Scrubbed Ticket should appear.
  4. Open it. You should see the scrubbed version with placeholders. Edit the box — restore anything wrongly hidden, hide anything missed — then Approve.

Test ticket to paste

P1: Sales order 39349230 cannot be saved, short dump in VA01.
Document number not available in database. Reported by Sarah Whitcombe
from the Hamilton branch, contact 021 445 9922 or
sarah.whitcombe@gallagher.co.nz. Check table LIKP for plant ELEC.
Customer 0001045992 affected since this morning.

What you should see

  • Redacted: the person's name, the phone number, the email address, the customer number — each as a numbered placeholder such as <PERSON_1>, <EMAIL_1>.
  • Left alone: VA01, LIKP, and the sales order number 39349230 — transaction codes and table names are protected, and document numbers aren't treated as personal data.
  • Possibly wrongly redacted: plant ELEC or Hamilton branch. If so — good. That's exactly the correction the reviewer step exists for, and restoring it is the behaviour you're demonstrating.

If something goes wrong

Scrub step fails at runtimeMost likely the OAuth credentials or token URL. In the cockpit, open NER_SCRUBBER and confirm Token Service URL matches the url value in aicore-key.json with /oauth/token on the end. Check the run log in Monitoring → Process and Workflow Instances for the actual error.
401 / unauthorizedClient ID or secret mismatch. Re-paste both from the key file.
404 from the scrubberDestination URL wrong. It must end with /v2/inference/deployments/daedcfe9342d21a7 and nothing after.
Nothing gets redactedCheck the mode input is live and text is mapped to the form field, not left empty.
No task in My InboxThe Approval step's recipient isn't set to you. Edit, set Users to your email, re-release and re-deploy.

When it works, you've demonstrated the whole thing: a ticket goes in, personal data comes out redacted by a local engine inside your boundary, a human sees exactly what was hidden and corrects it, and only the approved text moves on. The triage call is the one step still missing, and it needs nothing more than the MCP server's auth header name.
